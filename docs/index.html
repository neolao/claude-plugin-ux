a claude code plugin

You describe the need.
ux designs it.
Then builds it.

It first understands your application — who uses it, on which platform, with which existing components — then proposes a UX adapted to the need, previews it as a clickable prototype, implements it with your own building blocks, and reviews the result. Everything it learns and decides is written to a .ux/ folder, committed alongside the code.

why ux

A UX process, not a paint job

Every step a careful design process takes by discipline, the plugin takes by workflow — grounded in your product, your users, and your own components.

01

Never assumes silently

/ux:clarify interviews you in rounds — every question whose prerequisites are settled, numbered, each with a recommended answer grounded in the product facts. Facts are looked up in the code and .ux/; only decisions come to you.

02

Understands before designing

/ux:discover detects the UI stack, inventories screens, components and tokens, captures the running app, and interviews you about users, jobs and constraints — the result grounds every later decision.

03

Proposes a UX adapted to the need

/ux:design frames the need against the product context, consults specialized expert agents in parallel, and presents 2–3 options that differ in interaction model — each justified by product facts — before writing the flow, its screens with every state, and a decision record.

04

Decides the look and feel once

/ux:style documents the intent of an existing design system, or proposes 2–3 visual directions — palette, typography, density, shape, motion — each previewed as a style tile; the chosen one becomes the source every screen draws its tokens from.

05

Validates cheaply

/ux:prototype builds a single-file clickable HTML prototype from the spec, styled with the project's own tokens, every state reachable, published for review before a line of production code exists.

06

Implements with your own building blocks

/ux:implement maps the spec to existing components — reuse, extend, create, in that order — builds state by state, localized and accessible, then verifies it in the running app.

07

Reviews the user-facing result

/ux:review runs six read-only review agents in parallel and returns a numbered findings list; /ux:audit applies the same agents plus a heuristic pass to the existing UI and produces a prioritized report, ready to feed back into /ux:design F<n>.

the toolbox

Eight commands, one workflow

CommandPurpose
/ux:discover [description]Understand the application: stack, tokens, screens, components, captures, user interview → .ux/product.md, .ux/inventory.md
/ux:clarify <topic>Grill the user in rounds about a need, a product, a visual direction or a plan until nothing is silently assumed — standalone, or run automatically by discover / design / style / implement
/ux:style [--redesign] [hints]Define the look and feel once per product: document the existing design system's intent, or propose 2–3 visual directions with style-tile previews → .ux/style.md
/ux:audit [path|screen]Heuristic audit of the existing UI with the review agents → prioritized .ux/audit/YYYY-MM-DD.md
/ux:design <need> | F<n> | NNNPropose 2–3 adapted UX options, write the chosen flow + screen specs + decision
/ux:prototype NNN | <slug>Build and publish a clickable HTML prototype; iterate; mark the flow validated
/ux:implement NNN | <slug>Implement the spec in the codebase, verify in the running app, review, mark implemented
/ux:review [path|diff] [--fix]UI/UX review of a change or path; --fix applies High/Medium fixes

the agents

Two families, one axis each

An ◆expert prescribes before the code exists — consulted by /ux:design and /ux:implement. A ▲reviewer critiques after — run by /ux:review and /ux:audit. Experts answer in a fixed shape (REQUIREMENTS / RISKS / SCENARIOS); reviewers are read-only and report only findings with a file:line or a capture as evidence.

the record

Everything it decides, next to your code

Created by /ux:discover, meant to be committed — every session and every teammate reads it before touching the UI.

.ux/
├── product.md          # who, what, platform, constraints, vocabulary
├── inventory.md        # the UI as it is: stack, tokens, screens, components, patterns, gaps
├── style.md            # look and feel: intent, palette, typography, density, shape, motion
├── flows/NNN-slug.md   # one flow per need — status: designed → validated → implemented
├── screens/<slug>.md   # one spec per screen, all five states covered
├── decisions/NNN.md    # UX decisions with rejected options (append-only)
├── prototypes/*.html   # single-file clickable prototypes
├── captures/            # screenshots of the real app (baseline, audits, after implementation)
└── audit/YYYY-MM-DD.md # prioritized findings

typical flow

From empty repo to a shipped screen

  1. /ux:discover — once per project (re-run when the product or UI changes a lot).
  2. /ux:style — or --redesign to evolve an existing system; the look and feel is decided once, then reused everywhere.
  3. /ux:audit — to see where the existing UI hurts users most.
  4. /ux:design "Let operators duplicate a fixture with its children" — or /ux:design F2 to fix an audit finding.
  5. /ux:prototype 001 — to validate with the product owner before any code.
  6. /ux:implement 001 — builds it; the review runs automatically at the end.
  7. /ux:review — on any UI change made outside this workflow.

Steps 1, 2, 4 and 6 open with a /ux:clarify session: it looks up what the code and .ux/ already say, then grills you only on what remains open, round by round, before anything is written.
